# Verus — your true weight

An iOS app that puts activity, workouts, weight, body composition and progress
on one timeline, fed from Apple Health wherever the phone already knows the
answer.

**Status: in development.** All five screens are built. Food logs manually
and shows intake against expenditure; the photo-to-calorie path is gated on a
technical spike described at the bottom of this file.

| | |
|---|---|
| **Platform** | iOS 18+, iPhone only |
| **Language** | Swift 6, strict concurrency |
| **UI** | SwiftUI, Swift Charts |
| **Health data** | HealthKit — steps, energy, workouts, weight |
| **Storage** | On device. No account, no server, no network except the Health store |
| **Project file** | Generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` |

---

## The design law

> **The trend is the product.**

Every screen follows from that one line. The number in 60-point type is never
this morning's reading — it is the smoothed trend, with the raw figure
underneath it in grey. Daily weight is mostly water, and an app that puts the
scale reading first teaches you to react to noise.

## Running it

Prerequisites: Xcode 26+, and XcodeGen (`brew install xcodegen`).

```bash
xcodegen generate
open Verus.xcodeproj
```

`Verus.xcodeproj` is gitignored on purpose. `project.pbxproj` conflicts on
every branch that adds a file, and `project.yml` is readable in a diff.

```bash
# build and test from the command line
xcodebuild test -scheme Verus \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

To run on a device, set your own team under **Signing & Capabilities** — the
project deliberately hard-codes no team, so it builds for the simulator on any
machine.

## Decisions worth reading

These are the judgement calls. Each has a test that fails if the decision is
undone.

**The projection cannot flatter you.** `TrendEngine.Projection` has no case
that returns a date from a guess — `notEnoughData`, `tooSlowToProject`,
`movingAway` and `reached` are all reachable states. An honest answer is
representable and an invented one is not, so "never promise a faster date than
the data supports" is a property of the type rather than a thing to remember
while writing a view.

**Smoothing is an EWMA at α = 0.10**, roughly a nineteen-day centre of mass. A
6 lb salty-dinner spike moves the line under a pound. Days with no weigh-in
carry the trend forward rather than being skipped, so a fortnight away from the
scale does not render as one overnight drop.

**HealthKit never says a read was denied.** Apple treats "this app may not see
your steps" as itself private, so a denied type returns an empty result
indistinguishable from a genuinely empty week; only *write* permission is
reported honestly. There is therefore no `isAuthorized` in this codebase,
because there could not be an honest one. `ActivityStore.SourceState` models
what the app can actually know — whether it asked, and whether anything came
back — and the UI says "either there is no data for this month, or Verus was
not granted access", never "you denied access".

**Sample data is never silent.** Any state other than `.live` draws a banner
saying the figures on screen are not the user's own. An empty calendar teaches
nothing about what the app does; a calendar labelled as sample teaches both.

**One internal unit per quantity.** Mass is kilograms everywhere and converted
at the edges; tape measurements are centimetres. The one place a unit can be
confused is the boundary, and the way to make that impossible is to have
exactly one internal unit.

**Progress photographs stay on the device.** Written inside the app container,
never to the shared photo library and never to a server — there is no upload
path in the file to go wrong later. Each is written with
`.completeFileProtection`, so the bytes are unreadable while the phone is
locked; the default is weaker and the default is not good enough for
photographs somebody took of their own body. Deleting removes the file, not
just the row pointing at it.

**An unlogged day is not a deficit.** A day where Health reports 2,000
calories burned and nothing was eaten into the app is an unlogged day, not a
2,000 calorie deficit — and treating it as one would flatter the user and
poison every average built on top of it. `EnergyBudget.Balance` has a separate
`burnOnly` case for exactly this, and `averageNet` leaves those days out.

**A day in progress does not break a streak.** At nine in the morning nobody
has walked 15,000 steps, and an app that zeroes a three-week streak every
midnight teaches you to stop opening it. Today counts once it qualifies;
otherwise the count starts at yesterday. A day with *no reading at all* does
break it — there is no evidence it was walked.

**Averages are over days that reported, not over seven.** A week where the
phone was left at home twice was not a week of five-sevenths effort.

**The two goals are not independent.** Holding lean mass constant, a body-fat
target implies a weight, so `BodyComposition` can say where the second goal
lands relative to the first — "hitting 150 lb would leave you above 10% body
fat; that target needs about 146 lb at your current lean mass". The assumption
is carried into the UI rather than buried: lose muscle alongside fat and the
number moves.

## Testing

**85 tests**, covering the parts where being wrong is silent: the trend
maths, month-grid date arithmetic, activity rollups and streaks, the progress
timeline's deltas, body-composition arithmetic, and the energy budget.

```bash
xcodebuild test -scheme Verus -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

Two conventions carry the suite:

- **The logic is pure and the clock is a parameter.** `TrendEngine`,
  `MonthGrid`, `ActivityRollup`, `ProgressTimeline` and `BodyComposition` take
  their `Calendar` and their "today" as arguments, which is why a flat month, a
  gaining trend or a Sunday-first locale can all be tested without waiting for
  one.
- **Tests pin the judgement calls, not just the happy path.** A slower pace
  must always project a later date. A finished week missing one day is still a
  finished week. Weekday headings must match the weekday of the date beneath
  them in every time zone — that last one exists because the first version got
  it wrong and 28 passing tests did not notice.

## Project structure

```
Sources/
├── App/            VerusApp, RootView, Info.plist, entitlements
├── Core/           Pure logic, no UIKit and no HealthKit
│   ├── TrendEngine.swift        smoothing, rate, projection
│   ├── MonthGrid.swift          calendar layout arithmetic
│   ├── ActivityRollup.swift     weeks, streaks, week over week
│   ├── ProgressTimeline.swift   photo/measurement timeline and deltas
│   ├── BodyComposition.swift    lean mass, goal relationships
│   └── HealthKitService.swift   the only file that imports HealthKit
├── Model/          Plain value types
└── Features/       One folder per screen, each with its store and views
Tests/              Swift Testing, mirroring Core/
```

`ActivitySource` is the seam that keeps HealthKit out of the views:
`HealthKitService` and `SampleActivitySource` both satisfy it, so every screen
is previewable on a machine with no Health permissions.

## Known gaps

Stated plainly, because a README that only lists what works is a sales page.

- **Photo food logging is not built.** It is gated on a spike: photograph
  real meals, weigh them, run them through a vision model, compare estimate to
  truth. If estimates are too far off on real food to be useful with
  correction, the product changes shape. The Food screen says this on its own
  empty state rather than hiding the gap, and the `FoodEntry.Source` enum
  already carries a `photoEstimate` case so the storage format will not have
  to change when it lands.
- **The weight write to HealthKit is unverified.** The read path and the
  permission flow are confirmed on the simulator; proving a write lands needs a
  real device.
- **No watch app, no Android, no barcode scanning, no sharing.** All are
  deliberate v2 scope.
- **Sample data appears when Health has nothing**, clearly labelled. That is a
  development convenience as much as a product decision, and it should be
  revisited before any release.
